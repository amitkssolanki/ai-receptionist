# Proposal: explicit customer confirmation as a server-enforceable state

**Status: proposal only. Nothing in this document is implemented.** It follows from call #8 (see
`docs/voice_agent/verification_log.md`), where `submit_order` ran 2.1 s after `get_cart` and before the caller had heard the
read-back, and the server accepted it.

## 1. What the server enforces today

`app/services/order_taking.rb`, under the call/order row locks:

| Step | Server state | What it proves |
|---|---|---|
| `add / update / remove` | `cart_version` += 1 | the cart changed |
| `get_cart` (`#read_back`, line ~36) | `read_back_version = cart_version`, `read_back_at` | **a tool call named `get_cart` ran at that version** |
| `submit_order` (`#submit`, line ~113) | needs `cart_version` argument == current == `read_back_version` | the model quoted the current version, and `get_cart` ran at it |

What it does **not** prove: that the read-back was *spoken*, that the caller *heard* it, or that the caller said *yes* to it. The
read-back rule stops a model from submitting a cart it never fetched or that changed since; it cannot stop a model that chains
`get_cart` and `submit_order` in one breath. `readback_text` is generated by the server, but nothing checks it was said.

## 2. Evidence the server could have that does not come from the model

Vapi sends the server events the model does not control. Facts about what the baseline call (#7) received, from the frozen
fixture (`serverMessages` was unset, meaning all defaults):

- `conversation-update` (46 in a 3 min call): carries the conversation so far (`messages` / `messagesOpenAIFormatted`) with
  roles `user` / `bot` / `tool_calls` / `tool_call_result`, each with `time`, `secondsFromStart` and, for user speech, `endTime`.
  The frozen copy has the intermediate lists **trimmed**, so their arrival order relative to the tool-call webhooks is **not
  verified**.
- `speech-update` (66): `started` / `stopped` per role.
- `transcript` was not among the events received; the API enum lists `transcript[transcriptType="final"]`, which would need to
  be added to the assistant's `serverMessages` (and to `assistant.json` / `vapi:check`).

So the raw material exists: what the assistant said after a given `get_cart`, and what the caller said after that. Unknown, and
to be measured before relying on it: whether the caller's "yes" reaches the server before the model's `submit_order` does.

## 3. The state to add

Per order, derived and enforced by the server (all under the existing `call_logs -> orders` lock order):

```
cart_open ──get_cart(vN)──▶ read_back_requested(vN)
   ▲                              │ assistant speech after that get_cart contains the read-back (items + total)
   │ any cart change              ▼
   └───────────────────── read_back_spoken(vN)
                                  │ next caller utterance is an unambiguous yes; no cart change since
                                  ▼
                          customer_confirmed(vN) ──submit_order(vN)──▶ submitted
```

- A cart change (version bump) returns to `cart_open`. A caller utterance after the read-back that is not a clear yes (a
  question, "wait", "actually", "no", "add…") ends the window: `read_back_challenged`; the model must re-read.
- Storage: two columns on `orders` (`customer_confirmed_version`, `customer_confirmed_at`), nothing else. **No utterance text is
  stored or logged** (the classifier runs in memory; logs keep the existing rule: event type and call id only).
- New refusal in `#submit`, after the existing read-back checks: `customer_confirmation_required` (message: read the order back
  aloud in full, wait for the caller to say yes, then submit). A second, softer code `customer_confirmation_pending` if the
  server has seen the read-back but not yet an answer.
- The console board gains a row: `customer confirmation: not heard / heard "yes" at T+02:21 (server-observed) / challenged`,
  and a submit event row states which state it found. Same style as the existing read-back row.

## 4. Ways to obtain the "yes", best first

| Option | Idea | Verdict |
|---|---|---|
| **A. Server-observed conversation** | The server derives confirmation from Vapi's `conversation-update` (or final `transcript`) events, not from the model. | **Recommended.** The model cannot assert what the caller did not say. Needs an event-source change and a conservative classifier; timing to be measured. |
| B. Model-attested tool | New tool `confirm_readback(cart_version)` the model calls after the caller says yes. | Weak alone: the model can call it in the same turn as `get_cart`. It only helps combined with A (the server verifies the attestation), at which point the tool is redundant. |
| C. Out-of-band confirmation | Caller presses a key, or replies to an SMS, or clicks a button in the console. | Strongest for real orders; changes the UX and does not fit a browser voice demo. Worth keeping in mind for production. |
| D. Minimum gap between `get_cart` and `submit` | Refuse if too soon. | Rejected by the owner, and weak: it proves time passed, not consent. |

## 5. Design of option A

**Derivation is stateless and idempotent.** `conversation-update` repeats the whole history, so the server should not track
"new" utterances. On each event (or on `submit_order`), compute from the message list: find the latest `tool_calls` message for
`get_cart` (time T0, version from its result); look at `bot` messages after T0 for the read-back content (every item name and the
total appear); then the first `user` message after that speech; classify it. The result is a pure function of the list plus the
order's current `cart_version`, so repeated or reordered deliveries cannot double-count.

**Classifier.** Conservative and explicit: accept only short utterances made of an allow-list of affirmatives ("yes", "yeah",
"yep", "correct", "that's right/correct", "sounds good", "go ahead", "confirm"), and reject anything containing a negation or a
change word ("no", "wait", "actually", "but", "change", "remove", "add", "instead"). Anything else is *not confirmed* (never
"probably yes"). Known limits: speech-recognition errors, a "yes" meant for something else, sarcasm, and a caller who confirms
a wrong order that was read correctly (call #8's two Margheritas): the server cannot judge intent, only that the caller agreed.

**Race.** The caller's "yes" and the model's `submit_order` are separate webhooks. On a miss the submit is refused with
`customer_confirmation_pending`, and the model tells the caller it is confirming and tries once more. The handler for the
conversation events must not hold the call lock while waiting; a bounded wait inside `submit_order` is rejected for that reason.

**Configuration.** `serverMessages` += the chosen event; `assistant.json`, the `vapi:check` expectation, `assistant.md` and the
drift tests change with it. Webhook volume is modest (call #7: ~112 conversation/speech events in 3 minutes) and each handler
returns immediately unless the order has an open read-back.

**Modes, to avoid stranding orders if the events do not arrive:** `off` (today) -> `shadow` (compute the state, record
"would have refused" on the submit event row and the console, refuse nothing) -> `enforce`. The default stays `off` until live
shadow data shows the events arrive before submits.

## 6. What call #8 would have done

`get_cart` 14:47:05, then `submit_order` 14:47:07.995. The last caller utterance before it was "Pickup." (not an affirmative),
and the read-back was spoken only afterwards. Under `enforce` the submit is refused (`customer_confirmation_required`); the agent
reads the order back ("one Margherita, one Margherita with extra cheese, one Garlic Knots, $35.50"); the caller says yes;
`customer_confirmed_version = 3`; the submit is accepted. (The duplicate Margherita would still be there; it is now a display
observation, not a refusal.) This is an illustration from the transcript and timings, not a test.

## 7. Verification plan

- Classifier table tests (accepts, rejects, near misses, empty, very long).
- State derivation tests over recorded conversation lists (call #7's final list; call #8's transcript with reconstructed
  roles/times) and synthetic ones: chained `get_cart`+`submit` refused; yes after a spoken read-back accepted; yes to an earlier
  question refused; negative after read-back challenged; cart change after yes invalidates; repeated full-history events are
  a no-op.
- Scenarios in `Evaluation` (the garlic-knots harness): each above, through the real server path.
- Concurrency (real threads, as in the Step 7/8 tests): a confirmation event racing a cart mutation and a submit; lock order stays
  `call_logs -> orders`.
- Live: shadow mode on calls #2..N; record how often and how early the events arrive relative to submits, and every disagreement
  between the classifier and a human reading the transcript.

## 8. Effort and decisions

Roughly 8-12 hours: enable the event and record its real shape (~1 h); derivation + shadow recorder + console row (~4-6 h); live
shadow calls and analysis; enforcement flag, prompt wording and drift/config updates (~2-3 h).

Decisions for the owner: (1) which event source (`conversation-update` is proven to be sent; `transcript` finals need the config
change); (2) shadow first (recommended) or enforce directly; (3) how strict the affirmative list should be; (4) whether option C
belongs in the roadmap for real phone orders.
